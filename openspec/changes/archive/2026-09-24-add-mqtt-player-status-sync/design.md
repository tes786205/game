# Design

## Context

Single-player Phaser 4 game (Parcel 2 bundler) with no networking. See
proposal.md for motivation. Relevant current state:

- `src/game/scenes/Game.js`: the local player (`tobias`) is driven by a rex
  virtual joystick whose update handler already computes the vocabulary we
  need to publish — `animation` (`stopped|walking|running`), `orientation`
  (`up|down|left|right`), plus `x`/`y` from arcade physics. The peer sprite
  today is a static `lola` at a fixed position with a collider that starts
  `GameOver` on contact.
- Scene flow: `Boot -> Preloader -> MainMenu -> Game -> GameOver`
  (`src/game/main.js` registers the scene list).
- Both spritesheets are 1216x1216 / 64x64 frames — animation frame numbers
  defined for `tobias` apply verbatim to the `lola` texture, so remote
  rendering is symmetric for either role.
- Specs for this change: `specs/multiplayer/pairing/spec.md`,
  `specs/multiplayer/status-sync/spec.md`.

## Goals / Non-Goals

**Goals:**

- Two browsers rendezvous via room code, claim characters, and play the
  existing movement game while seeing each other.
- Minimal moving parts: broker is dumb transport, each client is authority
  over only its own pose (Phaser owns all local collision, per the
  scope decision in the proposal).

**Non-Goals:**

- World/events plane (cells, zombies, ark, flashlight) — namespace reserved
  only; see proposal.md non-goals.
- Authentication, privacy, broker operation — public broker accepted.
- Gameplay win/lose semantics for the two-player game.

## Decisions

### D1: MQTT client and broker configuration

Use **`mqtt.js`** (browser build, native WebSocket transport) connecting to
`wss://` — it is the standard JS MQTT client, supports Last Will,
retained-message reading, and QoS 0/1 needed here.

Broker URL from env var **`MQTT_BROKER_URL`**, which Parcel inlines at build
time from `.env` (Parcel 2 replaces `process.env.X` literals at bundle time).
Default when unset: `wss://broker.emqx.io:8084/mqtt` (public, no auth).
*Alternative considered:* `test.mosquitto.org` (also fine; EMQX picked as it
is the commonly available public WSS endpoint — swappable via env var, so
this is a default, not a lock-in).

### D2: Topic scheme

```
game/<room-code>/slot/<char>            retained   {id, state:"joined"|"left"}
game/<room-code>/player/<client-id>/state  QoS0 10-15 Hz, retained,
                                                ALSO the Last Will topic
                                                (will payload {"state":"left"})
game/<room-code>/world/...              RESERVED, never published
```

The **state topic doubles as the presence channel**: the will payload
(`state:"left"`) arrives on the same topic the poses arrive on, so the
receiving client needs exactly one subscription per peer and no separate
presence logic. Slot claims are separate (keyed by *character*, not by
client id) because their whole purpose is arbitration: retained claims make
"who won" readable by late joiners.

*Alternative considered:* separate `presence/<id>` will topic — rejected:
two subscriptions and two code paths for what is one observable fact
("this player is/isn't here").

### D3: Identity and room codes

- `client-id`: `crypto.randomUUID()` per page session (fresh every load, so
  stale retained state from a previous session can never impersonate you).
- Room code: 4-character code from an unambiguous alphabet (no `0/O/1/I`),
  generated by the creator, typed by the joiner. **The code is the
  namespace** — anyone who knows it joins that game. Accepted: no sensitive
  data (proposal), and guessing a 4-char code among active rooms is a
  non-goal for a demo-scale game.

### D4: Character-claim race resolution

Both clients publish a retained claim to `game/<code>/slot/<char>` for the
character they want, then **read back what the broker retained**:

- own id retained → claim won.
- other id retained → claim lost → immediately claim the *other* character.

This converges with two players regardless of interleaving: two different
picks both win; one pick collides exactly once and the loser takes the
remaining slot. When a claim is lost, the loser overwrites the other slot
topic only if it is free (it will be, since the winner took the first).
Claims are cleared/overwritten by presence (`slot` claim kept in sync with
player presence; a `left` state on the player topic marks the slot free).

### D5: Publish loop

Fixed-rate publisher inside `Game.update()` behind a time accumulator
(every 66–100 ms → 10–15 Hz), publishing **even when stationary** (spec
requires it). *Alternative considered:* publish-on-change + heartbeat —
rejected: two code paths, and latest-wins QoS0 makes change-only publishing
buy nothing. Payload: exactly the spec contract
`{x, y, dir, anim, state}` — the joystick handler's existing vocabulary, so
publishing is a read of values the scene already computes.

### D6: Remote rendering with interpolation

Keep the **last two received snapshots** (with local receive timestamps).
Render the remote sprite at `lerp(prev, current, t)` where `t` is the
playback position through the gap between them, plus a small fixed delay
(~1 nominal interval, ≈100 ms) so a late message doesn't stall the sprite —
i.e., render ~100 ms behind the peer. `dir` and `anim` apply from the
*current* snapshot immediately (snapping direction/animation looks correct;
snapping position looks like teleporting).

*Alternatives considered:* (a) snap to latest — rejected: visible jitter at
10 Hz; (b) dead reckoning from velocity — rejected: complexity not justified
at 800x450 with slow walkers, and wrong turns would overshoot.

### D7: Game scene rework

`Game.js` becomes role-aware via init data (`{ room, clientId, char, peer }`):

- local sprite = `char` texture, joystick logic unchanged;
- peer sprite = other character texture, created at first `playing` message,
  driven by D6, removed on `left`.
- **The `tobias x lola -> GameOver` collider is removed** (this is the
  proposal's "reinterpreted"): with both sprites being real players, ending
  the game on contact would end every session on first meeting, and
  contact-based gameplay outcomes belong to the future world plane. Map
  collision for both sprites stays local (Phaser), per the scope decision.

### D8: New pairing scene

New scene `CharacterSelect` inserted between `MainMenu` and `Game`: create/
join UI, room-code display/input, claim race (D4), waiting state, starts
`Game` when both slots are held by live players.

## Risks / Trade-offs

- **[mqtt.js + Parcel 2 bundling friction]** (browser field, `ws` shims,
  node globals) → mitigate: **spike first** — task 1.1 bundles a bare
  connect/publish/subscribe before any scene work; if mqtt.js misbehaves,
  fall back to a minimal raw WebSocket MQTT 3.1.1 implementation or
  `async-mqtt`-free alternative before building on top.
- **[Public broker instability / rate limits / no SLA]** → game degrades:
  pairing stalls or poses freeze. Accepted for now; broker URL is config
  (spec), so a private broker is a one-line `.env` change. No state is
  lost because there is no durable state in plane 1.
- **[Short room codes are guessable]** → accepted (no sensitive data);
  random codes keep accidental cross-talk rare. Reserved `world/` namespace
  keeps future event traffic isolated anyway.
- **[Clock skew / network jitter distorts lerp timing]** → the delay-buffer
  approach uses *receive* timestamps only (no cross-machine clocks), so
  skew cannot affect rendering; jitter only shifts the effective delay.
- **[Retained state topic shows a stale pose after peer reload]** → fresh
  `client-id` per load means a stale retained message belongs to an id no
  longer present; the joiner's claim arbitration and `left` will prevent a
  ghost sprite (worst case: stale pose appears until first live message
  arrives ~100 ms later).

## Migration Plan

Additive change; rollback = revert the commit (single-player flow intact —
`MainMenu` could point back to `Game` directly). Deploy: `yarn build` with
or without `MQTT_BROKER_URL` in `.env`; no infrastructure to provision.

## Open Questions

- **Peer disconnect mid-game: does the game end, or does play continue
  solo?** Removal of the remote sprite is specified; *game-over policy* is
  gameplay and belongs to the future world-plane change. Does not affect
  this design or its tasks.
- **Rejoin the same room after refresh?** Deferred: a reload creates a new
  `client-id` and the select screen flow re-runs; whether a half-played
  session can be re-entered is a world-plane concern (re-syncing revealed
  cells doesn't exist yet).
